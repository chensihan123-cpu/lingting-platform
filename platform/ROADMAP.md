# 灵听后续功能落地方案

更新：2026-09-20。以下是规划，不代表功能已经实现。

## 当前起点

已有：浏览器录音/文件上传 → 本地AST推理 → SQLite与WAV归档 → 人工复核 → 本地告警处理；模拟终端走同一HTTP接口。地图新增Leaflet + OSM街道底图、终端弹窗、录音入口、视角保持和离线点位回退。

## 实现顺序

1. 先保证服务容易启动、连续采集可靠，拿到一台板子完成真实设备接入。
2. 采集目标场景录音、建立带人工标签的测试集，测量识别效果和误报。
3. 按实际需要增加鸟种/两栖识别、通知、账号和服务器部署。
4. 有长期数据后开展节律分析；定位、多源联动作为独立专项验证。

## 逐项解决办法

| 未实现能力 | 具体实现办法 | 需要提供什么 | 完成时如何验收 |
|---|---|---|---|
| 重启后自动运行 | 将Python服务做成操作系统服务或服务器容器，配置故障重启、健康检查、日志轮转；本机先完善一键启动与端口检测 | 明确长期用本机还是服务器；自启动属于单独部署配置 | 重启后地址可用、服务异常可恢复、旧数据不丢失 |
| 持续监听 | 浏览器原型用AudioWorklet持续分帧并上传；长期采集由终端进程完成，环形缓存保留事件前后音频；限制上传队列，标记缺测 | 采样率、每天采集计划、网络和供电条件 | 连续运行至少24小时、记录丢包/断网恢复情况、时间线无静默缺口；浏览器后台休眠不作为可靠采集方案 |
| 真实板子接入 | 为终端编写采集代理，统一格式并上传音频、采集时间、设备编号及心跳；加入设备鉴权、幂等上传、断网缓存与补传 | 板子型号/系统、麦克风接口、联网方式、电量检测方式、GPS来源 | 一台真实设备上传成功；模拟断网后按原采集时间补齐，重复上传不重复建档 |
| 连续数据处理能力 | 先测当前CPU每10秒音频的推理耗时；若多设备积压，增加持久任务队列、工作进程、资源限额，按性能选择服务器或轻量边缘模型 | 同时在线设备数、上传频率、最大等待时间 | 在目标设备数量下长期运行无持续积压，失败可重试并可观测 |
| 具体鸟种识别 | 在AST旁增加独立物种模型（可评估BirdNET）；按模型自身采样要求处理原始音频，保存物种名、片段起止、模型版本和分数；人工复核 | 项目区域与季节、重点物种列表、当地有标注的真实录音 | 在本地独立测试集报告逐类精确率/召回率及混淆，不用演示样例代替评估 |
| 两栖物种识别 | 先核对选定模型是否覆盖目标蛙类；未覆盖类别收集正样本、相似物种和雨虫噪声负样本，训练专用分类器 | 目标物种、标注人员、不同设备/天气的录音 | 与相似蛙鸣、虫鸣、流水和雨声对照测试；未知声音不强行归类 |
| 自动微调 | 建立音频片段和复核标签的数据集版本；离线训练，按设备/时间拆分训练验证测试集，检查旧类性能；通过评估后发布新模型并可回滚 | 足够数量及质量的人工标签、训练资源、指标目标 | 新类改善且旧类退化不超约定阈值；可定位每条预测所用模型版本。未经复核的伪标签不直接更新线上模型 |
| 误报控制 | 增加逐类别阈值、连续窗口确认、相邻事件合并、告警冷却和人工误报反馈；分别保留命中告警的标签/分数及Top-1类别 | 现场背景噪声和真实异常样本、业务上允许的误报/漏报水平 | 测量每天每设备误报数与目标事件召回率，规则命中证据可回溯 |
| 微信/短信等通知 | 后端发件任务队列接企业微信机器人、邮件或短信服务；加入告警去重、重试、发送状态和失败日志 | 明确接收人、渠道授权/密钥、发送频率和费用上限 | 先向指定测试接收人验证一次，触发同一事件不反复轰炸，发送失败可追踪 |
| 用户与权限 | 增加登录、密码散列/身份平台、管理员/复核员/巡护员角色、项目与设备权限、操作人审计 | 用户角色、组织关系、是否分多个保护区 | 不同角色只能访问授权数据，复核和派单能追溯到操作者 |
| 公网与多设备部署 | 使用生产级Web服务、反向代理与HTTPS、设备令牌、上传限流、监控告警；开发和生产分开 | 服务器、域名、设备网络、部署预算 | 外部授权设备可以接入，未授权请求被拒绝，断电重启可恢复。不直接将现有标准库HTTP服务裸露公网 |
| 大规模音频存储 | 将音频迁移至对象存储，元数据使用PostgreSQL；分页检索、保留期限、按日期分区/索引、备份与恢复演练 | 设备数、录音占空比、保留多久、预算 | 按实际负载压测检索/上传，随机抽样回放，并从备份恢复一段指定时段数据 |
| 季节节律与声景变化 | 记录有效采样时长、设备更换、天气等影响因素；加入周/月/季节对比和声景指标；缺测单独标记，与专家调查交叉验证 | 数月到跨季节的连续可比录音、环境数据和生态人员支持 | 输出带采样覆盖和不确定性说明的趋势，不能只凭鸟鸣片段数推断种群增长或生态恢复 |
| 卫星/地形与离线底图 | 选择有授权的影像/地形服务，或将允许离线使用的区域数据制成自托管瓦片；提供底图切换，保留来源和许可 | 目标区域、底图许可、离线范围、服务器资源 | 点位在各底图上对齐；离线断网测试可用；不能批量下载OSM官方公共瓦片作为离线包 |
| 多终端声源定位 | 至少多个同步采集通道、准确终端坐标，保存同步误差；评估互相关/TDOA定位及误差范围 | 多通道/多设备硬件、时钟同步方案、已知声源位置的试验场地 | 在多组已知位置和噪声下报告定位误差与失败率；设备地图标点不算声源定位 |
| 相机/无人机/巡护联动 | 定义统一事件与任务接口：声音告警→人工确认→创建巡护/复核任务→设备返回图片/视频→同一事件归档；自动控制另做专项验证 | 厂商API/SDK、设备型号、任务权限、现场操作人员 | 首先完成一条人工确认的跨设备任务及回传归档，再讨论自动调度 |

## 音频格式需要提前调整的一点

当前平台将输入规范化为16kHz WAV，足够复用现有AST。未来增加物种模型时，应保存设备的原始高采样率音频，在各模型前分别重采样。已降为16kHz的录音无法恢复丢失的高频信息；不要等采集完大量数据后才决定物种模型和采样规格。

## 对接硬件时先收集这张清单

- 板子型号、CPU/内存/系统、可用存储；麦克风型号、通道数、接口。
- Wi-Fi/以太网/蜂窝网络，是否长期断网；供电方式和可读取的电量数据。
- 采样率/位深、采集时段、GPS坐标系、时间同步方式。
- 优先识别的声音/物种，以及误报和响应时延要求。
- 预计设备总数、音频保留期、部署场地、已有相机/无人机接口。

## 数据量估算（未压缩，仅供规划）

16kHz、16-bit、单声道为每秒32,000字节，全天连续录音约2.76GB/设备/天（十进制），尚未计备份与数据库。10台连续录制30天约829GB。最终容量需按原始采样率、压缩方式和录音占空比重新计算。
